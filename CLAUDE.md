# Kalthum for Peace — Automated Timesheet System

## What this is

An internal monthly timesheet and multi-step approval platform for Kalthum for Peace, replacing a manual paper/Excel process. Staff log daily attendance (Present/Absent/Public Holiday/Leave) for a month; timesheets route through a role- and department-dependent approval chain (Team Lead → Department Head → SPM/HR, with several self-approval and parallel-approval special cases) before becoming a permanent, immutable record.

Full product requirements: [context/PROJECT_CONTEXT.md](context/PROJECT_CONTEXT.md) — source of truth, do not invent requirements beyond it.

## Tech stack

- **Frontend/backend:** Next.js (App Router) + TypeScript
- **Styling:** Tailwind CSS
- **Database/Auth:** Supabase (PostgreSQL + Supabase Auth + Row Level Security)
- **Deployment:** Vercel (frontend), Supabase (backend), target domain `timesheet.kalthum4peace.org`
- **Migrations:** Supabase CLI, version-controlled SQL files under `supabase/migrations/`

## Design direction

Confirmed 2026-09-15. Applies the personal design-taste principles (warm-restrained-confident, one accent, one quiet signature detail, function wins over purity) to this project's actual brand and audience — see the proposal artifact from that session for the full palette/type specimen.

- Brand asset: [Product Logo/kfp-logo.jpg](Product%20Logo/kfp-logo.jpg) — dove mark + KFP wordmark, white on solid blue.
- Accent — `#0270CE` ("KFP blue"): sampled directly from the logo's background fill (six-point pixel sample via .NET `System.Drawing`, not eyeballed). Used for primary actions, headings emphasis, links.
- Warm neutral base — `#FAF6EE` (page background), `#FFFEFB` (card/surface, one step lighter), `#2A241D` (warm near-black body text, not pure black). Picked fresh for this project.
- Typeface — Work Sans (400/500/600/700), one family for both headings and body, via Google Fonts. Chosen over Inter/Space-Grotesk-style defaults for warmer humanist letterforms and legibility at the small sizes a daily-attendance grid needs — fits the "digital paper form for non-technical staff" goal in PROJECT_CONTEXT §25.
- Signature detail: a single-stroke line flourish (echoes the dove's continuous-line style, not a literal copy) placed once, under the wordmark in the persistent app header. Nowhere else — do not repeat it on individual screens or components.
- Header wordmark text is responsive, CSS-only (Tailwind `sm:` breakpoint, no JS width detection): "Kalthum For Peace Timesheet" at `sm` and up, "KFP Timesheet" below it — two `<span>`s toggled with `sm:hidden`/`hidden sm:inline`, plus `whitespace-nowrap` on the wrapping span so neither string ever wraps internally regardless of how much the nav links squeeze the flex row at narrow widths (the nav wraps instead, which is the acceptable trade-off). Verified in the real browser at both 375px and 1024px, light and dark.
- Status color is two separate decisions, not one blanket rule:
  - Staff's own daily attendance and own timesheet status: plain text, no color-coding. One person reviewing their own record — the status already is the information; color would just be decoration on top of it.
  - Approver's pending-approvals list (Team Lead, Dept Head, SPM, HR): color-coded chips — pending `#875E17` on `#FBEEDA`, returning `#B24422` on `#FBE7DE`, approved `#3B723D` on `#E7F1E5`. Many timesheets scanned at once to decide what needs attention — the legitimate functional case for color.
  - Every chip also carries a text label, so status is never conveyed by hue alone (colorblind-safe per WCAG 1.4.1). Chips are light-tinted pills with colored text; the primary-action button is a solid `#0270CE` fill with white text — distinct in both hue and form, so "needs attention" never reads as "this is a button."
- Contrast verified against WCAG AA (4.5:1 body text / 3:1 large text) before locking this in, not assumed:
  - Warm ink on ivory base 14.24:1, warm ink on card surface 15.21:1, white on accent button 4.99:1.
  - Chip/tint text initially measured short on three values and was darkened at the same hue until it cleared 4.5:1: pending chip 3.18→5.03:1, approved chip 4.28→4.95:1, accent text on tinted accent surface 4.31→4.91:1. Returning chip passed on first measurement (4.70:1).
- Banned outright for this project: gradient/glow buttons, heavy drop shadows, emoji-as-icons, star-glyph ratings, reflexive traffic-light coding outside the approver-scanning case above, stark pure-white backgrounds as the default.
- When scaffolding Tailwind, encode the tokens above (not re-derived approximations) as the theme's color/font values.

## Standing rules

- Read the actual current repo/schema state before proposing or building anything — never assume prior state, even from an earlier session's summary.
- Any schema change, migration, or RLS policy change is dry-run and shown in full before being applied for real. No exceptions, even for something that "looks obviously safe."
- Every write to a live Supabase project (schema or data) is confirmed explicitly before running — never inferred as "probably fine." The dev Supabase project counts as live once it holds anything worth not losing.
- Deploy schema and dependent code together, or explicitly sequence which lands first.
- Large/risky changes go on a separate branch, verified before merge to main — never merged speculatively "to save time."
- Verify behaviorally, not just by reading code — e.g. RLS policies get tested by actually attempting the access they're supposed to block, not just confirmed to exist by reading the policy.
- A surprising or too-clean result gets a second look before being trusted, especially if it contradicts something already confirmed.
- A permanent identifier, once assigned to a record, is never recalculated from other fields.
- If something surfaces that's genuinely an OPEN DECISION or a contradiction with PROJECT_CONTEXT.md, stop and report it rather than silently picking an assumption and continuing. Clean, unambiguous implementation work proceeds without round-tripping for approval on every step.
- No production changes of any kind unless explicitly requested.
- `.env` for all secrets, no hardcoded values anywhere in source, ever, including "temporarily."

### Portability (this project specifically)

Built in a personal dev environment now; production will belong to Kalthum for Peace on their own Vercel/Supabase accounts. For every implementation decision, ask: would moving this to Kalthum's own production environment later require a code change, or only a configuration change? If the former, reconsider the approach.

- Never hardcode environment-specific values or secrets anywhere in code, config, or migration files.
- Keep dev and production configuration fully separate (`.env` per environment; nothing assumes a specific account/project by default).
- All schema changes are version-controlled migration files, applied in sequence — never a manual dashboard edit, even in dev.
- Nothing in the codebase, CI, or deployment scripts creates a hard dependency on the developer's personal GitHub, Vercel, or Supabase accounts specifically. The app must work identically if pointed at a different Supabase project via `.env`.
